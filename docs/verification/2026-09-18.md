## Design points that did not survive contact

* **`ENABLE_SIGNUP=false` as a safety net for a failed bootstrap.** It is
  not one: upstream lets the first account in regardless (see the facts
  table). The start script still seeds it, so the stored value starts
  closed, and it refuses every value the bootstrap would fail on (a
  missing secret, an email without `@`, a password under 8 or over 72
  bytes), but the control that closes the window is the **loopback verify
  pass**. It runs whenever the installation cannot be shown to have an
  account: no install marker, no `webui.db`, or a `SELECT count(*) FROM
  user` that is not a positive number (a query error counts as "run it").
  Then upstream is started on `127.0.0.1:8079` (8078 if Dockhold's port is
  8079), the script waits up to 240 s for its health check, signs in with
  the bound admin credentials from Python (the password stays in the
  environment), and only on a 200 with role `admin` writes the marker,
  stops the loopback server with SIGTERM, waits for it, and execs the real
  server on Dockhold's port. Nothing listens on that port until the
  account is proven. A sign-in failure prints `The admin account could not
  be created, or the bound WEBUI_ADMIN_EMAIL and WEBUI_ADMIN_PASSWORD do
  not match the existing admin. Check them on this app's Variables tab and
  restart.` (the second half is the restore-without-marker case, tested
  below), a loopback server that dies prints one line pointing at the
  lines above it, a health timeout prints one line; none of the three
  writes a marker, so the next start repeats the pass, and upstream
  creates the admin only while no users exist, which is exactly the state
  a failed pass leaves behind. An established install with an account
  skips the pass, so the extra start is paid once. The smoke test proves
  the public port refuses every connection until the marker exists, that a
  bootstrap failure past the value checks (a user table that refuses
  inserts) ends in the one line with no marker and no public answer, with
  and without the marker present, and that the established path takes
  half the first start's time. The README says why the bootstrap is
  strict.
* **The marker alone was not enough.** The first version of the pass keyed
  on the marker only. A reviewer reproduced: marker and key present,
  `webui.db` with an empty user table and a failing insert, and the public
  port opened with no admin; a stranger's signup got the admin role. Hence
  the user-count condition above and the "marker present, user table
  empty" cases in the suite.
* **Wording.** "Redeploy" is not a thing the platform does for a Run-path
  app: Restart starts the same build, and only a connected repository
  rebuilds on push. Every README claim was rewritten around that; a
  Run-path app stays on its build and upgrades happen on the Develop path.
  The storage refusal now says the app restarts on its own once storage is
  attached, which the platform does.
* **"Malformed means under 32 bytes decoded."** Upstream's own file
  decodes to 24 bytes (32 base64 characters). The guard checks for one line
  of at least 32 base64 characters, which is exactly what upstream writes;
  a check at 32 decoded bytes would have refused every upstream-generated
  file.
* **"One warning at most" for the static copies.** Twenty error lines.
  Handled as above.
* **Marker before key.** Writing the established-install marker before the
  key exists would let an interrupted first start produce "established, no
  key" and a permanent refusal. The start script creates the key first
  (atomically, via a temp file and rename), runs the verify pass, and
  writes the marker last, so a kill at any moment leaves either nothing, or
  a key file (and possibly an admin account) that the next pass finds by
  signing in, or a consistent pair. The five interrupted-start cases below
  cover 1 s, 5 s, right after the admin was created, the moment the
  loopback health first answers, and during the loopback sign-in.

Measurements from the same run:

* **First start on fresh storage at 2 GB: 66.0 s to the public `/health`.**
  The install marker (end of the loopback verify pass) appeared at 34.7 s,
  the real server answered 31 s later. One start of this image is about
  32 s here (31.7 to 33.3 s across runs; 36.5 s for the unmodified
  upstream image on the same machine): Alembic runs its migration chain,
  then the embedding model loads. **Second start (established install):
  31.3 s**, no verify line, one server start in the log. So the verify pass
  costs one extra cold start, once per installation. The platform's
  crash watch after start does not probe the port, so a first start that
  takes two to three minutes on slower hardware is not itself a problem;
  a slow first start that then refuses is (see production acceptance).
* **The public port during the first start:** polled every half second
  from the helper; every attempt before the marker existed was refused
  (curl code 000), the first 200 came after it. Same on every interrupted
  first start's retry and on the fault case's recovery start.
* **Memory at `--memory 2g`:** `memory.peak` 683 MiB at the moment
  `/health` first answered, 717 MiB after signin and one PDF upload,
  `memory.current` 705 MiB after 10 s idle. The number that matters for
  sizing is the idle figure: this image holds about 700 MiB of Python,
  torch and the embedding model before any user does anything.
* **At `--memory 1g` (measurement, not a case):** first start (verify pass
  plus public start) 64.8 s, signin worked, the PDF upload returned 200,
  `memory.peak` 716 MiB, not OOM-killed, still running.
* **Log hygiene:** after every start (first, second, settings-changed,
  bound-key, each interrupted retry, the SIGTERM retry, both fault cases,
  the restore case, the 1 GB run) the log was grepped for both admin
  passwords, both provider keys, the 73-byte password, the key file's
  content and the bound `WEBUI_SECRET_KEY` value. None appeared. Upstream
  prints the admin email itself on two lines at bootstrap; the password,
  the provider key and the session key never appear.
* **SIGTERM during the verify pass** (the platform's stop signal): the
  start script forwarded it to the loopback server, waited for it, and
  exited 143; no marker, key file present; the retry ran the pass, kept the
  port closed until the marker, came up with one admin and the same key.
  The case is phase-based: the signal goes out once the log shows the
  verify line and the loopback server's own start line, and only while
  the marker does not exist (a clock-based 20 s landed after the pass on
  a GitHub runner, where the whole pass took under 20 s, and the case
  was reported UNKNOWN-shaped as a failure; it now reports UNKNOWN with
  the reason if the marker already exists when the signal would go out).
  **Time from SIGTERM to container exit, measured locally at three
  points of the pass:** 1.2 s during the import phase (verify line plus
  3 s), 1.3 s right after the loopback server's start line, 1.3 s once
  the loopback health answers. The health loop sleeps one second between
  polls and the trap runs after the current command, so about a second
  is the floor; nothing in the pass holds the signal longer, and it
  cannot approach the platform's stop grace. The retry after each of
  those was healthy.
* **Marker present, user table empty:** with the admin rows deleted and
  the insert trigger back, the pass ran on the marker alone being present
  (the user count is what decides), refused with the mismatch line, and
  the public port never answered; with the trigger dropped, the pass ran
  again, created the admin, and the app came up.
* **Restore without the marker on a populated database:** the admin
  changed the password in the panel (`POST /api/v1/auths/update/password`;
  the token used for the change still got 200 afterwards, so a password
  change does not end sessions without a session store, as the README
  says), the marker was removed, and a start with the original secrets
  bound ran the pass, got a 400 on sign-in, printed the mismatch line and
  exited 1 with no marker and no public answer. Binding the current
  password ran the pass, signed in, wrote the marker, healthy.
* **Forged headers:** the case proves only that `X-Forwarded-*` and `Host`
  grant nothing (protected endpoints still 4xx without a token), which
  also holds without the headers. What the headers do change: upstream
  starts uvicorn with `--forwarded-allow-ips "*"`, so the client address in
  the access log followed `X-Forwarded-For` (`203.0.113.9:0` for a request
  from the helper). Recorded, not asserted; behind Dockhold only the edge
  reaches the app and what it does with a client's own header is the
  edge's, not this image's. So 1 GB survives the local workload; 2 GB is
  the recommendation because 717 MiB is already 70% of 1 GB with nothing
  loaded but one page, and the acceptance run on the platform measures a
  real chat.
* **Token lifetime:** 604,800 s from the token's own claims (7 days).
* **PDF ingestion offline:** a one-page PDF (generated by the test, 671
  bytes) uploaded with `?process=true` was extracted, split, embedded with
  the bundled `all-MiniLM-L6-v2` and added to the vector store; the file
  status became `completed` with the probe sentence in its content. The
  log has no download attempt and no Hugging Face line. Same result at
  1 GB.
* **Outbound calls without network:** `GET /api/models` triggered the
  provider model list; the log shows `Connection error: Cannot connect to
  host api.openai.com:443` and the endpoint returned 200 with an empty
  list. `GET /api/version/updates` returned the current version as latest.
  The app stayed healthy through both.
* **Which side owns each setting after the first start** (restart with
  every variable changed at once): admin email and password, provider base
  URL and key, Ollama on/off, signup, public URL, session lifetime and
  default user role all kept their first-start values; the changed

* **Session key:** the token from the first start still worked after a

  admin, `/api/config` says signup is disabled, and a stranger's signup

  `{"total":1,"roles":["admin"]}`: the stranger is the admin. This is
  the case the start script's value checks exist for.
* **Static refresh:** zero `Permission denied` lines with the Dockerfile's
  directory chown; favicon and splash served with 200.
* **The admin email is in the log:** upstream prints it on two lines at
  bootstrap (`Creating admin account from environment variables: <email>`
  and `Admin account created successfully: <email>`). The password, the
  provider key and the session key never appear.

## Not verified here

* Anything that needs the platform: the deploy link, the form, secret
  binding, the edge, HTTPS, custom domains, the platform's rollback after a
  failed start, message
  streaming through the edge, App storage growth. See the next section.
* A real provider reply (no network in the test). Which providers are
  claimed depends on production acceptance: OpenAI is the default;
  OpenRouter is named in the README because it is a plain
  OpenAI-compatible endpoint, and the acceptance run should confirm a
  model list and a streamed reply from it before the recipe names it.
* Disk full on App storage. The PocketBase starter's test covers the
  pattern; this image's first start alone writes about 1 MB and a
  meaningful fill would need uploads of real size. Left for production
  acceptance on a small volume if wanted.
* Build on the platform's builder and its time budget. The local build is
  the 1.7 GB pull plus two seconds.
